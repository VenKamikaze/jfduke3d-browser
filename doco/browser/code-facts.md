# Code facts

What the code actually does, verified in brief 00 against this repository at `browser/00-setup` with the submodules at their pinned commits (jfbuild `5950d14`, jfaudiolib `ff1b31d`, jfmact `731c0cc`, vnet `v0.5.0`). The game is upstream jfduke3d `55c5f95` (`master`); nothing in `src/` has been changed yet. Paths are relative to the repository root; `jfbuild/…` and `jfaudiolib/…` are in the submodules. Line numbers are for those commits.

Every fact has a file:line. The facts were read from the source, not copied from [`porting-jfduke3d.md`](https://github.com/VenKamikaze/jfsw-browser/blob/claude/doco/browser/porting-jfduke3d.md) (the hand-over write-up, in jfsw-browser); where the code disagrees with it, §13 says so. Runs of the real binary on the shareware GRP are marked "(run)": see [`building.md`](building.md) and `scripts/run-headless.sh`.

Two things that differ from jfSW and matter everywhere:

- **There is no `net.c`, `sync.c` or `demo.c`.** The netcode is in `src/game.c` (§2) and the demo code too (§9). The globals are in `src/global.c`, declared in `src/duke3d.h`.
- **The game is compiled as C and linked as C++:** `.c` files with `-std=c99` (`Makefile:50`), the final link with `g++` (`Makefile:169`). `src/duke3d.h:269` renames the global `sync[]` to `dsync[]` with a macro.

Timing: `TICRATE 120` (`src/duke3d.h:100`), `TICSPERFRAME (TICRATE/26)` (`src/duke3d.h:101`), which is **4** (integer division): the simulation runs **30 tics a second**, not 40 as jfSW does. `totalclock` is advanced by `sampletimer()` (`jfbuild/src/sdlayer2.c:754`), which the game calls from `getpackets()` (`src/game.c:451`) and `faketimerhandler()` (`src/game.c:780`) and the engine calls from `handleevents()` (`jfbuild/src/sdlayer2.c:1587`). `MOVEFIFOSIZ 256` (`src/duke3d.h:74`), `RECSYNCBUFSIZ 2520` (`src/duke3d.h:73`).

## 2. The netcode

### 2.1 Data

- `input` (`duke3d.h:262-267`): `signed char avel, horz; short fvel, svel; unsigned int bits`. `inputfifo[MOVEFIFOSIZ][MAXPLAYERS]` and `sync[MAXPLAYERS]` (`src/duke3d.h:270`, `src/global.c:93,98`), `loc` is the local input being built (`src/global.c:93`).
- Counters (`src/global.c:105`): `movefifoend[i]` (inputs received for player `i`), `movefifoplc` (next tic to run), `movefifosendplc` (the master's next tic to forward), `fakemovefifoplc` (prediction), `syncvalhead[i]`, `syncvaltail`, `syncvaltottail`, `syncval[i][MOVEFIFOSIZ]` (`src/global.c:90-91`), `myminlag[]`, `mymaxlag`, `otherminlag`, `bufferjitter` (starts at 1, `src/global.c:174`; reset to 1 in `clearfifo`, `src/premap.c:1376`).
- Input bits (the comment table is `src/sector.c:2426-2454`; they are built in `getinput`, `src/player.c:1943-2001`): bits 0-7 jump, crouch, fire, aim up/down, run, look left/right; 8-11 weapon; 12 steroids; 13/14 look up/down; 15 night vision; 16 medkit; **17 multiplayer save/load request** (then 18 = save(1)/load(0), 19-22 slot: `src/player.c:1934-1941`); 18 centre view; 19 holster; 20 inventory left; 21 pause; 22 quick kick; **23 aim mode** (`myaimmode`); 24 holoduke; 25 jetpack; **26 quit** (`gamequit`); 27 inventory right; 28 turn around; 29 open; 30 inventory; 31 escape. A menu or typing state sends `bits = gamequit<<26` and zero movement (`src/player.c:1878-1888`).
- `TIMERUPDATESIZ 32` (`src/game.c:42`): every 32nd tic carries lag-trim bytes.
- Players: `connecthead` and `connectpoint2[]` (the mmulti list, `jfbuild/include/mmulti.h:15-18`), `numplayers` (the live count, it goes down when a player leaves: `src/game.c:9064`), `ud.multimode` (the count the game uses, `src/game.c:9065`), `playerswhenstarted` (`src/game.c:7949`), `playerquitflag[i]` (`src/global.c:111`).

### 2.2 `getpackets()` (`game.c:445-771`)

Line numbers in this table and the text below are `src/game.c` unless a file is named. Order: `sampletimer()` (`:451`); `OSD_DispatchQueued()` only when not in a game (`:454`); `return` if `numplayers < 2` (`:456`); then `while ((packbufleng = getpacket(&other, packbuf)) > 0) switch (packbuf[0])`. `getpacket` and `sendpacket` are mmulti's (`mmulti.h`), the only game calls are the `sendpacket` sites in §2.8. Packet types (first byte; "M/S relay" = in master/slave mode the master forwards it to everyone but the sender, `(!networkmode) && (myconnectindex == connecthead)`):

| Byte | Meaning | Size (payload) | Handled at | Notes |
|---|---|---|---|---|
| 0 | **master -> slave: the tic's inputs of every live player** | `1 + [one timer byte per live slave on every 32nd tic] + one flag byte per live player + the changed fields + the master's pending sync bytes` | `:475-536` (built `:992-1054`) | The flag byte says which of `fvel`(2 bytes), `svel`(2), `avel`(1), `bits` bytes 0-3 (1 each), `horz`(1) follow, as deltas from the previous tic. The player's own entry is skipped on receive (`:498-500`). A `bits & (1<<26)` entry clears `playerquitflag` (`:511`). After the fields, every remaining byte is a sync byte, stored for **every player but myself** (`:515-524`). With `movesperpacket > 1` the input is repeated (`:526-532`). |
| 1 | **slave -> master: one tic of the slave's input** | `2 + changed fields + sync bytes` | `:537-566` | `packbuf[1]` is the flag byte. Sync bytes are stored for the sender (`:554-558`). |
| 4 | chat message | `2 + text + NUL`, `packbuf[1]` = destination (255 = everyone) | `:568-598` (sent `:2184-2212`, `:6561-6573`) | M/S relay; a message for another player is forwarded to just that player (`:579-583`). Text is copied into `recbuf[80]` (`:587-590`). |
| 5 | **new game** (level, volume, skill, monsters_off, respawn monsters/items/inventory, coop, marker, ffire) | 11 | `:600-629` (sent `game.c:6250-6265`, `menues.c:3847-3880`, `:3890-3920`) | M/S relay. Resets every player's weapons and inventory, then `newgame` + `enterlevel(MODE_GAME)`. |
| 6 | **player announcement:** index, `BYTEVERSION`, name, 10 weapon choices, aim mode, auto-aim, weapon-switch | `3 + len(name)+1 + 10 + 3` | `:630-664` (sent `getnames`, `:7602-7633`) | M/S relay. **The version check:** `packbuf[2] != BYTEVERSION` -> `gameexit("\nYou cannot play Duke with different versions.")` (`:642-643`). | 7 | RTS voice macro (plays sample N) | 2 | `:665-679` (sent `game.c:6592-6600`) | M/S relay. Plays only if an RTS file is loaded (`:672`) and sound is on. |

| 16 | peer-to-peer: the first input (resets the fifos), then as 17 | | `:713-716` | Only in `networkmode == 1`. |
| 17 | peer-to-peer: one tic of a player's input | `1 + [timer bytes from the head on every 32nd tic] + flag + fields + sync bytes` | `:717-759` (sent `:841-913`) | |

Notes: all multi-byte values are little-endian bytes written by hand (no struct copies), so native/wasm agree. Players come from mmulti as `other`; a slave only ever has the master as peer in M/S mode (`game.c:418`, `:2201`, `:6572` etc.).

### 2.3 `faketimerhandler()` (`game.c:774-1058`), the per-tic sender

Called from the main loop while a tic is due (`src/game.c:8136-8137`) and from `jfbuild/src/engine.c` (about 30 sites inside long drawing loops, e.g. `jfbuild/src/engine.c:900`, `:1495`, `:4627`, `:8053`), so network and input run while the engine draws. Line numbers below are `src/game.c`. Steps:

1. `sampletimer()`; return unless `totalclock >= ototalclock + TICSPERFRAME` and `ready2send` (`:780-781`). `ototalclock += TICSPERFRAME` (`:782`).
2. `getpackets()`; return if `getoutputcirclesize() >= 16` (`:784`; mmulti's stub returns 0, `jfbuild/src/mmulti.c:644`).
3. Return without sending if any peer's `movefifoend` is more than 200 tics behind ours (`:786-788`).
4. `getinput(myconnectindex)` (`:790`) and the average over `movesperpacket` (`:792-811`; `movesperpacket` is 1 by default, `src/global.c:170`; `-f2/-f4` set 2/4, `src/game.c:7042-7054`). With `movesperpacket > 1` the intermediate tics only repeat the last input (`:797-803`).
5. Single player (`numplayers < 2`): with `-q` (fake multiplayer) other players get empty inputs, or computer inputs with `-a` (`:813-824`); return.
6. Lag measurement and `bufferjitter` adaptation (`:826-839`).
7. **Peer-to-peer (`networkmode == 1`):** build packet 16/17 and send it to everyone (`:841-913`).
8. **Slave (`myconnectindex != connecthead`):** build packet 1 and `sendpacket(connecthead, …)` (`:914-971`). Every 32nd tic it trims `totalclock` by `TICSPERFRAME*i` to keep the master's inputs just ahead (`:917-925`).
9. **Master:** if some player's `movefifoend` is not past `movefifosendplc`, send a `127` resend nudge and return (`:973-981`). Otherwise loop (`:983-1057`): return unless **every live player** has an input for `movefifosendplc` (`:985-986`); build packet 0 (`:992-1054`), `sendpacket` it to every live slave (`:1048-1054`), `movefifosendplc += movesperpacket` (`:1056`).

So the master forwards at the master's own timer tick (and from the `getpackets()` call at `:784`), not the moment the last input arrives. Slaves never talk to each other: all traffic is slave <-> master.

### 2.4 `moveloop()`, `domovethings()` and prediction

- **`moveloop()`** (`src/game.c:8464-8482`): if `numplayers > 1`, run `fakedomovethings()` for every input not yet predicted (`:8468-8469`); `getpackets()` (`:8471`); `bufferjitter = 0` when single player (`:8473`); then
  `while (movefifoend[myconnectindex] - movefifoplc > bufferjitter)` { stop if any player has no input for `movefifoplc` (`:8476-8478`); `if (domovethings()) return 1;` } (`:8474-8480`). It returns 0 normally. **Nothing in the loop looks at `MODE_EOL`** (§5).
- **`domovethings()`** (`src/game.c:8955-9142`, `char`): returns **1 only at `:9007`**, after a successful `loadplayer` of a multiplayer saved game requested by an input with bit 17; every other path returns 0 (`:9141`). Order of a tic: save/load requests (`:8960-9010`) -> `lockclock += TICSPERFRAME` (`:9013`) -> HUD timers (`:9015-9037`) -> copy `inputfifo[movefifoplc]` into `sync[]` and `movefifoplc++` (`:9041-9043`) -> `updateinterpolations()` -> **players that sent the quit bit** are removed (`:9047-9083`: `numplayers--`, `ud.multimode--`, `"%s is history!"`, `quickkill`, `deletesprite`; and `gameexit(" \nThe 'MASTER/First player' just quit the game…")` when the master leaves in M/S mode, `:9081-9082`) -> **the sync byte** (`:9085-9092`, §2.5) -> `record()` when recording a demo (`:9094`) -> `global_random = TRAND; movedummyplayers();` when not paused (`:9096-9100`) -> per player `cheatkeys(i)`, and unless paused `processinput(i)`, `checksectors(i)` (`:9102-9111`) -> unless paused: `movefta`, `moveweapons`, `movetransports`, `moveplayers`, `movefallers`, `moveexplosions`, `moveactors`, `moveeffectors`, `movestandables`, `doanimations`, `movefx` (`:9113-9129`) -> `fakedomovethingscorrect()` (`:9131`) -> every other tic `animatewalls`, `movecyclers`, `pan3dsound` (`:9133-9138`).
- **Prediction.** `fakedomovethings()` (`src/game.c:8516-8952`) moves only the local player's copies `myx`, `myy`, `myz`, `myang`, `myhoriz`, … from the local inputs not yet confirmed (`inputfifo[fakemovefifoplc]`, `:8525`). It reads the real `ps[myconnectindex]` and the map, and it writes: the `my*` variables, `myxbak[]…` (`:8944-8948`), `fakemovefifoplc++` (`:8949`), and **temporarily `sprite[p->i].cstat`** (`&= ~257` at `:8529-8530`, restored at `:8951`; every `goto` in the function ends at that label). The engine calls it makes (`getzrange`, `clipmove`, `pushmove`, `updatesector`) take the `my*` variables by pointer. It does not call `TRAND`/`krand`. `fakedomovethingscorrect()` (`:8484-8514`) compares the predicted position with the real `ps[]` at the confirmed tic (`:8494-8495`), and if they differ copies the real state into the `my*` variables and re-predicts (`:8497-8512`). It reads `p->aim_mode` (`:8563`, `:8918`), which is the *confirmed* mode, not the one in the unconfirmed input: a one-tic prediction difference after a toggle, harmless to the real state.

### 2.5 The sync value and `checksync()`

- **The value** is one byte per 8 tics: `if ((numplayers >= 2) && ((movefifoplc&7) == 7))` (`src/game.c:9085`): `ch = randomseed & 255`, plus, for every player, `(posx + posy + posz + ang + horiz) & 255` of `ps[i]` (`:9087-9089`), stored in `syncval[myconnectindex]` (`:9090-9091`). Nothing else (no sprites, sectors, health, ammo, CON state) is covered. It is computed **after** the tic's `movefifoplc++` and **before** `processinput`/the actors run (`:9043` vs `:9085` vs `:9102`), so it checks the state at the end of the *previous* tic.
- **Transport:** each machine puts its own pending sync bytes at the end of its packets (`:902-906`, `:963-967`, `:1042-1046`). The master stores each slave's bytes in `syncval[slave]` (`:554-558`); each slave stores the master's bytes in `syncval[i]` for every `i != myconnectindex`, **including the other slaves** (`:515-524`).
- **`checksync()`** (`src/game.c:1090-1122`), called once per displayed frame from the main loop (`src/game.c:8127`): while every player has an unchecked byte at `syncvaltottail`, compare each player's byte with `connecthead`'s (`:1094-1108`); any difference sets `syncstat = 1` (`:1098-1104`); `syncstat = 0` when only one player is left (`:1110`). Both the master (slave bytes against its own) and each slave (its own against the master's) detect a mismatch; peer-to-peer machines compare all.
- **The message:** `printext256(… "Out Of Sync - Please restart game" …)` and a second line (`:1112-1116`), **on the screen only**: there is no `buildprintf`, so a headless test cannot see it, and a hidden tab draws nothing. `syncstate` ("Missed Network packet!", `src/game.c:1117-1121`) is mmulti's obsolete variable (`jfbuild/src/mmulti.c:641`) that nothing sets, so that message never appears.
- Nothing resets `randomseed` except `resetprestat` (`src/premap.c:645`: `randomseed = 17`) and loading a saved game (`src/menues.c:365`). `krand()` is `jfbuild/src/engine.c:9693-9696`; `TRAND` is `krand()` (`src/duke3d.h:202`). Drawing and menu code in `src/` never calls `TRAND`/`krand` (the only `game.c` users are the simulation: `spawn`, the glass helpers, `domovethings`; `src/premap.c:448` is spawn-point choice).

### 2.6 `waitforeverybody()` (`src/premap.c:1288-1316`)

`return` if `numplayers < 2`. Send packet 250 to every other player, or only to the master if a slave in M/S mode (`src/premap.c:1293-1298`); `playerreadyflag[myconnectindex]++` (`src/premap.c:1299`); then `while (1)`: `handleevents()` (`src/premap.c:1303`), **`gameexit("")` on a quit event or Escape** (`src/premap.c:1305`), `getpackets()` (`src/premap.c:1307`), done when every player's counter has caught up (a slave in M/S mode only waits for the master, `src/premap.c:1309-1314`). ### 2.7 Version checks

`BYTEVERSION_JF 132` (`src/duke3d.h:66`); `BYTEVERSION = 132 + (PLUTOPAK ? 1 : (VOLUMEONE << 1))` (`src/duke3d.h:68`): regular 132, Atomic 133, shareware 134. `PLUTOPAK` is `conversion == 14` (`src/duke3d.h:51`), and `conversion` is set by the **compiled CON scripts** (`src/gamedef.c:31` default 13, set to 14 at `src/gamedef.c:1512` when the `gamestartup` command has the Atomic Edition's extra parameters, `src/gamedef.c:1495-1515`). `VOLUMEONE` is the identified GRP being the shareware (`src/duke3d.h:52`, `src/game.c:7856`). So the version byte covers the **GRP kind and the CON flavour**, not their contents. Checked at: packet 6 (`src/game.c:642`, gameexit on mismatch), demo open (`src/game.c:8173-8183`, prints "Demo is for …" and refuses), saved-game load (`src/menues.c:217`, FTA message 114).

## 3. Network set-up

### 3.1 How `networkmode` is chosen

- The game never chooses. `networkmode` is mmulti's variable (`jfbuild/src/mmulti.c:91`, initially -1) and is set from the arguments by `initmultiplayersparms` (`jfbuild/src/mmulti.c:723-885`): `-nm` / `-n0` = **master/slave**, `-nm:N` = N players (2..`MAXPLAYERS` 16, else "Invalid number of players", `jfbuild/src/mmulti.c:752-775`); `-np` / `-n1` = **peer-to-peer** (`jfbuild/src/mmulti.c:776-780`); a host name with no `-n` argument defaults to M/S with 2 players (`jfbuild/src/mmulti.c:861`); a relay (`-relay`, `-host-room`, `-room`) forces M/S and the room's player count (`jfbuild/src/mmulti.c:786-797`) and refuses `-np` (`jfbuild/src/mmulti.c:789-792`). The constants are `MMULTI_MODE_MS 0`, `MMULTI_MODE_P2P 1` (`jfbuild/include/mmulti.h:12-13`).
- **There is no rule by player count.** M/S works for 2 to 16 players. **Peer-to-peer works only for exactly 2** (`jfbuild/src/mmulti.c:879-884` returns 0 unless M/S with 2+ players, or `numplayers == 2`). The message at `src/game.c:9082` ("This only happens in 5-8 player mode as a different network scheme is used") is old text: it is printed when the master leaves **any** M/S game (`if (j < 0 && networkmode == 0)`, `src/game.c:9081`).
- The game reads the mode as `!networkmode` ("M/S") at `src/game.c:418, 464, 570, 603, 633, 668, 683, 2201, 2210, 6572, 6598, 7627`, `src/menues.c:1379, 3764, 3879, 3919`, `src/premap.c:1297, 1312`, as `== 1` (peer) at `src/game.c:841`, and as `== 0` at `src/game.c:9081`. In M/S mode the master re-transmits packets 126, 4, 5, 6, 7, 8 to the other slaves (§2.2).
- **For relay games** (brief 01, decision D5) no change is needed here: mmulti already picks M/S (`jfbuild/src/mmulti.c:786-797`).

| `src/sector.c:1394` | `checkhitswitch`, `lotag == 65535` (`src/sector.c:1392-1409`) | **only `ps[myconnectindex]`** (and `ud.level_number`), returns 1 |

The cheat codes only run when `numplayers < 2 && ud.recstat == 0` (`src/game.c:6407`, `src/game.c:5996`), so in a network game the live writers are the first four. All four run **inside `domovethings()` on every machine** (`processinput`, `checksectors`, `checkhitswitch` are simulation), and each sets the next `ud.level_number`/`ud.m_level_number` there too. The one writing only `myconnectindex` is consistent because each machine reads only its own `gm` (`src/game.c:8061`).

**The path:** `moveloop()` (`src/game.c:8464`) has the loop `while (movefifoend[myconnectindex] - movefifoplc > bufferjitter)` calling `domovethings()` (`src/game.c:8474-8480`) and **never tests `MODE_EOL`**. The write replaces the whole `gm` word (`= MODE_EOL`), which clears `MODE_GAME`, but the main loop only tests `gm&MODE_GAME` before the *next* `moveloop()` call (`src/game.c:8058`). So after the tic that sets `MODE_EOL`, the same `moveloop()` call keeps running every further tic whose inputs have arrived (and that has a buffer margin of `bufferjitter`); how many that is depends on how many tics the master had already forwarded, which differs by machine and by timing. Only then does the main loop see `MODE_EOL` (`src/game.c:8061`): `closedemowrite()` (`:8065`), `ready2send = 0` (`:8067`), `dobonus(0)` (`:8073`, §4), the episode-end handling (`:8075-8093`), `enterlevel(ps[myconnectindex].gm)` (`:8098`).

This is the same pattern as jfSW's L20 (`bugs.md`): machines can play different numbers of tics after the exit. What carries over into the next level in a co-op game (and in single player) is each player's weapons, ammo and inventory (`resetprestat` resets them only `if ((g&MODE_EOL) != MODE_EOL && numplayers < 2) || (ud.coop != 1 && numplayers > 1)`, `src/premap.c:656-660`) and health (`resetpspritevars`: `s->extra = ps[j].last_extra` after an exit, `src/premap.c:1195-1200`), so extra tics played after the exit change what a player has in the next level. **Not confirmed by a test and not fixed here**; the F3-style test belongs to brief A1.

## 12. Surprises and candidate entries for `bugs.md`

1. **`-nosetup` does not stop the startup window on a first run** (no `duke3d.cfg`): `configloaded < 0` opens it (`game.c:7809`). Headless runs unset `DISPLAY`.
2. **Quit during the network wait** returns from `Startup()` and then from `app_main` with initialisation unfinished (`game.c:7571-7574`, `:7904-7905`); jfSW's L4 has the same shape.
3. **SIGTERM / window close is the Escape key** in the game loop (`:8049-8052`), so it opens the menu instead of quitting; `waitforeverybody` and the startup wait do honour it (`premap.c:1305`, `game.c:7571`).
4. **Packet 8 (user-map game):** the sender writes the map name from byte 10 (`menues.c:3758`) and sends `10 + len` bytes; the receiver reads `ffire` from byte 10 (`game.c:696`) and copies the name from `packbuf+10` but with length `packbufleng - 11` (`:698-701`): friendly fire becomes the first character's ASCII value and the last character of the name is dropped. User-map network games only.
5. **A demo never exits by itself** (§9), unlike jfSW's.
6. **`newgame` waits for the skill-choice sound to end** (`premap.c:1024`) and the E3 end sequence waits for five voice clips (`game.c:9430-9442`): with a stalled mixer (a suspended browser audio context) these spin.
7. **Shareware quit shows two order screens** that wait for keys (`game.c:2088-2089`), also after a network error exit.
8. `myname` is not re-sent after a change (`osdcmds.c:352`); `auto_aim` and `weaponswitch` are sent once, in packet 6.
9. `MAXGROUPFILES` is 4 (`cache1d.c:389`): the main GRP plus three `-g` files.
10. Peer-to-peer mode is limited to 2 players by mmulti (§3.1), though `game.c` has the 3-or-more-player code for it.

## 15. What brief 01 added and learnt

Brief 01 (`01-native-relay.md`) changed the game only; line numbers are `src/` at `browser/01-native-relay`. New files: `src/netgame.c`/`.h` (the shareware gate, relay failures, the sync log) and `src/testhooks.c`/`.h` (test-only hooks).

### 15.1 Where things are now

- **Arguments** (`checkcommandline`, `src/game.c`): `-testquit<N>`, `-testsync`, `-testnudge<T>`, `-testdump<name>`, `-teststate[<T>]` and `-allowsharewarenet` are matched **before** the big `switch (*c)`. They have to be: any other `-t…` is the respawn option (`case 't'`, "Respawn on"), `-a…` is "other player AI", `-r…` records a demo and `-h…` names a DEF file. For the same reason `-relay`, `-room` and `-host-room` **outside `-net`** are refused with a message (`-net`'s branch skips them when they follow it). **Test-only arguments, and `-allowsharewarenet`, go after `--` (or before `-net`)**: what follows `-net` up to `--` belongs to mmulti (§3.2).
- **`app_main`**: the early gate before `initmultiplayersparms` (`NetGameAllowedFor(gamegrp->game)`, only when no startup window will run; nothing has been opened, so a refused relay host makes no room), then `NetFailIfRelayFailed()` when the arguments are bad (so the game exits 1 instead of starting a single player game), the authoritative gate after **every** group file is mounted, `-g` extras included (`NetGameAllowed()` -> `NetDataIsShareware()`: `VOLUMEONE` or a `DUKESW.BIN` openable from anywhere; covers the startup window's Join and Host; `gametype` is never changed: a `-g` shareware GRP with no main GRP leaves `gametype` DUKE, i.e. the game believes it is registered), `Startup()`: `mmulti_vnet_setplayercap(VOLUMEONE ? 4 : MAXPLAYERS)` before the wait and `NetFailIfRelayFailed()` after it. The engine's own limit for `-host-room` is **8** (`MAXROOMPLAYERS`, `jfbuild/src/mmulti_vnet.c`), though the game allows 16 over plain UDP.
- **Main loop and `waitforeverybody`** call `NetLostCheck()` (relay session FAILED and `movefifoplc` unchanged for 2 s: message, `uninitmultiplayers()`, exit 1). Nothing tells the *other* players: a host that vanishes still stalls the rest (as jfSW's L18 left it).
- **`checksync()`** calls `NetSyncDiffers()` and `NetSyncChecked()`: `GAME OUT OF SYNC: sync check N (tic T), player P differs from the master` is logged for the first difference of each run of mismatches (§2.5's "on the screen only" is no longer true), and `NetSyncChecks` / `NetSyncMismatches` count. **Every machine compares** (§13, item 3): the master each slave's byte against its own; a slave its own against the master's, so a slave other than the diverging one never sees it (`test-desync.sh`).
- **`domovethings()`**: `TestTicHook()` just before `lockclock += TICSPERFRAME` (after the multiplayer save/load block, which can `return 1` without running a tic): the `-testnudge` and the `-testdump` record, before `movefifoplc++`; the sync byte is `TestSyncByte()` instead of the usual one when `-testsync` is on, taken **every tic** (`syncval` is a ring of `MOVEFIFOSIZ` = 256 bytes, so at most 256 tics may be in flight); `TestTicEnd()` just before `return 0`: `-testquit`. A quit calls `gameexit("")`, which skips the shareware order screens and the deathmatch totals (`*t == 0`), still runs `allowtimetocorrecterrorswhenquitting()` (about 0.3 s) and writes the config; before it a network game keeps acknowledging and resending for 1.5 s so a player a few tics behind can finish.
- **Packet 6** carries `BYTEVERSION + TestVersionSalt()` (8 with `-testsync`, else 0), checked on receipt: a player without the same `-testsync` is refused ("You cannot play Duke with different versions."). `-testquit` values need not match (a player that stops early stops the others, as in jfSW).
- **The tic counter** in `-testdump` and `-testquit` is `movefifoplc` (+1 in the dump), which `clearfifo()` zeroes in `enterlevel`, so it starts again at 1 in each level. It is the same in single player and in demo playback (`playback()` calls `domovethings()` too).
- The `.state` text (`-teststate`) and the hashes are made from one list of fields (`WalkState`, `src/testhooks.c`).

### 15.2 The `-testdump` file

`<name>`, 32 bytes per game tic, eight little endian 32 bit words: `tic` (1-based, from the start of the level), `randomseed`, then 32 bit FNV-1a hashes (over little endian 32 bit words) of `players` (`ps[]` of every connected player), `sprites` (every sprite in use, and the status and sector list orders), `hittype` (`hittype[]` of the sprites in use), `sectors`, `walls` and `other` (`ud`'s game fields, `global_random`, `everyothertime`, `earthquaketime`, the animation, cycler, animated wall and sprite-queue tables, `frags`, `po[]`, the player list). The record is of the state **before** the tic is moved. jfSW's record is 17 bytes (tic, nine sync bytes, one hash); Duke's has more parts because Duke has no nine sync functions and because a test that finds a difference should say which table. `tests/tools/testdump.py diff A B` prints the first differing tic and parts.

### 15.3 State that differs between machines (found by running two machines and diffing; input for A1)

Each was the **first difference** two idle machines showed, and each is left out of the hash with a comment in `src/testhooks.c`:

1. `hittype[i].dispicnum`: written by `animatesprites()` (`src/game.c:5747-5760`, `:5934`) to the picture last drawn, so it is what this machine has drawn so far. Drawing writes the simulation's tables.
2. `sprite[i].yoffset` of a player's sprite (`statnum` 10): `animatesprites()` writes it while the player is in the air (`src/game.c:5594-5595`).
3. `hittype[i].temp_data[0..5]` of the ambient sound sprites (`statnum` 11, `MUSICANDSFX`): `movefx()` (`src/actors.c:1158`) keeps T1, T2 and T5 as audio bookkeeping from this machine's `SoundToggle`, `AmbienceToggle`, free voices and the view point (§7's table). They differed every 119 tics in the first 2-player run.
4. `ps[].aim_mode`, `auto_aim`, `weaponswitch` (and `ud.wchoice`) of other players on a slave: bug **D1**. Not a local setting: a real disagreement about the game's state in games of three or more.
5. `ps[].actors_killed` and `max_actors_killed`: credited to `ps[myconnectindex]` for any kill (§7's table). Not observed to differ in the runs (the kills are few); left out because the code says they will.
6. Left out **without** having seen them differ, because the code says they are a machine's own: `ps[].palette` (a pointer), `gm`, `fta`, `ftq` (the on-screen message), `zoom`, `visibility`, `pals`, `refresh_inventory`, `name`. A1 should check them. (`pals_time` is hashed: deterministic; `loogiex`/`loogiey` stay out because `actors.c:2498` reads the local `xdim`.)

With these left out, 2, 3 and 4 idle players over a relay and 2 and 3 over UDP agree on every tic for 450 to 1500 tics, and a 3-player game ran 2795 tics without the hang jfSW found at tic 1522 (F1).

### 15.4 Demos

- **A recording game's dump differs from its playback's** (bug **D2**): the camera effectors (SE 27) are spawned visible only while `ud.recstat == 1` (`src/game.c:4671-4676`). Two playbacks of one demo give identical dumps.
- Playback of a demo goes through the logo first (about 15 s on shareware with no key press), then plays at the game's pace; `-testquit` ends it. A demo records only inputs, so an idle recording (what a headless run makes) is a weak determinism check; a later brief should record real play (jfSW's `tests/tools/synth_input.c` shows how).
- `-r` and `-testdump` work together; `closedemowrite()` runs from `gameexit("")`, so a `-testquit` run leaves a whole `demo1.dmo`.

### 15.5 Other things seen

- **The slot a joiner takes** is the order its first ping reaches the master (engine; as in jfSW), so "the third process started" need not be player 2: tests wait for the previous joiner before starting the next one when it matters (`test-desync.sh`).
- `wm_msgbox` with no display prints its text to stdout as well, so a refusal or failure shows twice in a headless log. Harmless.
- `-allowsharewarenet` and the cfg key are read before the GRP is identified; the game's `VOLUMEONE` limits (4 players, episode 1) are separate and unchanged.
- `make test` runs the baseline build, which does `git worktree add` on this repository and fetches the submodules from the forks (needs the network, once).
