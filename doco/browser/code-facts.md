# Code facts

What the code actually does, verified in brief 00 against this repository at `browser/00-setup` with the submodules at their pinned commits (jfbuild `5950d14`, jfaudiolib `ff1b31d`, jfmact `731c0cc`, vnet `v0.5.0`). The game is upstream jfduke3d `55c5f95` (`master`); nothing in `src/` has been changed yet. Paths are relative to the repository root; `jfbuild/…` and `jfaudiolib/…` are in the submodules. Line numbers are for those commits.

Every fact has a file:line. The facts were read from the source, not copied from [`porting-jfduke3d.md`](https://github.com/VenKamikaze/jfsw-browser/blob/claude/doco/browser/porting-jfduke3d.md) (the hand-over write-up, in jfsw-browser); where the code disagrees with it, §13 says so. Runs of the real binary on the shareware GRP are marked "(run)": see [`building.md`](building.md) and `scripts/run-headless.sh`.

Two things that differ from jfSW and matter everywhere:

- **There is no `net.c`, `sync.c` or `demo.c`.** The netcode is in `src/game.c` (§2) and the demo code too (§9). The globals are in `src/global.c`, declared in `src/duke3d.h`.
- **The game is compiled as C and linked as C++:** `.c` files with `-std=c99` (`Makefile:50`), the final link with `g++` (`Makefile:169`). `src/duke3d.h:269` renames the global `sync[]` to `dsync[]` with a macro.

Timing: `TICRATE 120` (`src/duke3d.h:100`), `TICSPERFRAME (TICRATE/26)` (`src/duke3d.h:101`), which is **4** (integer division): the simulation runs **30 tics a second**, not 40 as jfSW does. `totalclock` is advanced by `sampletimer()` (`jfbuild/src/sdlayer2.c:754`), which the game calls from `getpackets()` (`src/game.c:451`) and `faketimerhandler()` (`src/game.c:780`) and the engine calls from `handleevents()` (`jfbuild/src/sdlayer2.c:1587`). `MOVEFIFOSIZ 256` (`src/duke3d.h:74`), `RECSYNCBUFSIZ 2520` (`src/duke3d.h:73`).

## 2. The netcode

### 2.1 Data

- `input` (`duke3d.h:262-267`): `signed char avel, horz; short fvel, svel; unsigned int bits`. `inputfifo[MOVEFIFOSIZ][MAXPLAYERS]` and `sync[MAXPLAYERS]` (`src/duke3d.h:270`, `src/global.c:93,98`), `loc` is the local input being built (`src/global.c:93`).
- Counters (`src/global.c:105`): `movefifoend[i]` (inputs received for player `i`), `movefifoplc` (next tic to run), `movefifosendplc` (the master's next tic to forward), `fakemovefifoplc` (prediction), `syncvalhead[i]`, `syncvaltail`, `syncvaltottail`, `syncval[i][MOVEFIFOSIZ]` (`src/global.c:90-91`), `myminlag[]`, `mymaxlag`, `otherminlag`, `bufferjitter` (starts at 1, `src/global.c:174`; reset to 1 in `clearfifo`, `src/premap.c:1376`).
- Input bits (the comment table is `src/sector.c:2426-2454`; they are built in `getinput`, `src/player.c:1943-2001`): bits 0-7 jump, crouch, fire, aim up/down, run, look left/right; 8-11 weapon; 12 steroids; 13/14 look up/down; 15 night vision; 16 medkit; **17 multiplayer save/load request** (then 18 = save(1)/load(0), 19-22 slot: `src/player.c:1934-1941`); 18 centre view; 19 holster; 20 inventory left; 21 pause; 22 quick kick; **23 aim mode** (`myaimmode`); 24 holoduke; 25 jetpack; **26 quit** (`gamequit`); 27 inventory right; 28 turn around; 29 open; 30 inventory; 31 escape. A menu or typing state sends `bits = gamequit<<26` and zero movement (`src/player.c:1878-1888`).
- `TIMERUPDATESIZ 32` (`src/game.c:42`): every 32nd tic carries lag-trim bytes.
- Players: `connecthead` and `connectpoint2[]` (the mmulti list, `jfbuild/include/mmulti.h:15-18`), `numplayers` (the live count, it goes down when a player leaves: `src/game.c:9064`), `ud.multimode` (the count the game uses, `src/game.c:9065`), `playerswhenstarted` (`src/game.c:7949`), `playerquitflag[i]` (`src/global.c:111`).

### 2.2 `getpackets()` (`game.c:445-771`)

### 2.3 `faketimerhandler()` (`game.c:774-1058`), the per-tic sender

Called from the main loop while a tic is due (`src/game.c:8136-8137`) and from `jfbuild/src/engine.c` (about 30 sites inside long drawing loops, e.g. `jfbuild/src/engine.c:900`, `:1495`, `:4627`, `:8053`), so network and input run while the engine draws. Line numbers below are `src/game.c`. Steps:

1. `sampletimer()`; return unless `totalclock >= ototalclock + TICSPERFRAME` and `ready2send` (`:780-781`). `ototalclock += TICSPERFRAME` (`:782`).
2. `getpackets()`; return if `getoutputcirclesize() >= 16` (`:784`; mmulti's stub returns 0, `jfbuild/src/mmulti.c:644`).
3. Return without sending if any peer's `movefifoend` is more than 200 tics behind ours (`:786-788`).
4. `getinput(myconnectindex)` (`:790`) and the average over `movesperpacket` (`:792-811`; `movesperpacket` is 1 by default, `src/global.c:170`; `-f2/-f4` set 2/4, `src/game.c:7042-7054`). With `movesperpacket > 1` the intermediate tics only repeat the last input (`:797-803`).
5. Single player (`numplayers < 2`): with `-q` (fake multiplayer) other players get empty inputs, or computer inputs with `-a` (`:813-824`); return.
6. Lag measurement and `bufferjitter` adaptation (`:826-839`).
7. **Peer-to-peer (`networkmode == 1`):** build packet 16/17 and send it to everyone (`:841-913`).
8. **Slave (`myconnectindex != connecthead`):** build packet 1 and `sendpacket(connecthead, …)` (`:914-971`). Every 32nd tic it trims `totalclock` by `TICSPERFRAME*i` to keep the master's inputs just ahead (`:917-925`).
9. **Master:** if some player's `movefifoend` is not past `movefifosendplc`, send a `127` resend nudge and return (`:973-981`). Otherwise loop (`:983-1057`): return unless **every live player** has an input for `movefifosendplc` (`:985-986`); build packet 0 (`:992-1054`), `sendpacket` it to every live slave (`:1048-1054`), `movefifosendplc += movesperpacket` (`:1056`).

So the master forwards at the master's own timer tick (and from the `getpackets()` call at `:784`), not the moment the last input arrives. Slaves never talk to each other: all traffic is slave <-> master.

### 2.4 `moveloop()`, `domovethings()` and prediction

- **`moveloop()`** (`src/game.c:8464-8482`): if `numplayers > 1`, run `fakedomovethings()` for every input not yet predicted (`:8468-8469`); `getpackets()` (`:8471`); `bufferjitter = 0` when single player (`:8473`); then
  `while (movefifoend[myconnectindex] - movefifoplc > bufferjitter)` { stop if any player has no input for `movefifoplc` (`:8476-8478`); `if (domovethings()) return 1;` } (`:8474-8480`). It returns 0 normally. **Nothing in the loop looks at `MODE_EOL`** (§5).
- **`domovethings()`** (`src/game.c:8955-9142`, `char`): returns **1 only at `:9007`**, after a successful `loadplayer` of a multiplayer saved game requested by an input with bit 17; every other path returns 0 (`:9141`). Order of a tic: save/load requests (`:8960-9010`) -> `lockclock += TICSPERFRAME` (`:9013`) -> HUD timers (`:9015-9037`) -> copy `inputfifo[movefifoplc]` into `sync[]` and `movefifoplc++` (`:9041-9043`) -> `updateinterpolations()` -> **players that sent the quit bit** are removed (`:9047-9083`: `numplayers--`, `ud.multimode--`, `"%s is history!"`, `quickkill`, `deletesprite`; and `gameexit(" \nThe 'MASTER/First player' just quit the game…")` when the master leaves in M/S mode, `:9081-9082`) -> **the sync byte** (`:9085-9092`, §2.5) -> `record()` when recording a demo (`:9094`) -> `global_random = TRAND; movedummyplayers();` when not paused (`:9096-9100`) -> per player `cheatkeys(i)`, and unless paused `processinput(i)`, `checksectors(i)` (`:9102-9111`) -> unless paused: `movefta`, `moveweapons`, `movetransports`, `moveplayers`, `movefallers`, `moveexplosions`, `moveactors`, `moveeffectors`, `movestandables`, `doanimations`, `movefx` (`:9113-9129`) -> `fakedomovethingscorrect()` (`:9131`) -> every other tic `animatewalls`, `movecyclers`, `pan3dsound` (`:9133-9138`).
- **Prediction.** `fakedomovethings()` (`src/game.c:8516-8952`) moves only the local player's copies `myx`, `myy`, `myz`, `myang`, `myhoriz`, … from the local inputs not yet confirmed (`inputfifo[fakemovefifoplc]`, `:8525`). It reads the real `ps[myconnectindex]` and the map, and it writes: the `my*` variables, `myxbak[]…` (`:8944-8948`), `fakemovefifoplc++` (`:8949`), and **temporarily `sprite[p->i].cstat`** (`&= ~257` at `:8529-8530`, restored at `:8951`; every `goto` in the function ends at that label). The engine calls it makes (`getzrange`, `clipmove`, `pushmove`, `updatesector`) take the `my*` variables by pointer. It does not call `TRAND`/`krand`. `fakedomovethingscorrect()` (`:8484-8514`) compares the predicted position with the real `ps[]` at the confirmed tic (`:8494-8495`), and if they differ copies the real state into the `my*` variables and re-predicts (`:8497-8512`). It reads `p->aim_mode` (`:8563`, `:8918`), which is the *confirmed* mode, not the one in the unconfirmed input: a one-tic prediction difference after a toggle, harmless to the real state.

### 2.5 The sync value and `checksync()`

- **The value** is one byte per 8 tics: `if ((numplayers >= 2) && ((movefifoplc&7) == 7))` (`src/game.c:9085`): `ch = randomseed & 255`, plus, for every player, `(posx + posy + posz + ang + horiz) & 255` of `ps[i]` (`:9087-9089`), stored in `syncval[myconnectindex]` (`:9090-9091`). Nothing else (no sprites, sectors, health, ammo, CON state) is covered. It is computed **after** the tic's `movefifoplc++` and **before** `processinput`/the actors run (`:9043` vs `:9085` vs `:9102`), so it checks the state at the end of the *previous* tic.
- **Transport:** each machine puts its own pending sync bytes at the end of its packets (`:902-906`, `:963-967`, `:1042-1046`). The master stores each slave's bytes in `syncval[slave]` (`:554-558`); each slave stores the master's bytes in `syncval[i]` for every `i != myconnectindex`, **including the other slaves** (`:515-524`).
- **`checksync()`** (`src/game.c:1090-1122`), called once per displayed frame from the main loop (`src/game.c:8127`): while every player has an unchecked byte at `syncvaltottail`, compare each player's byte with `connecthead`'s (`:1094-1108`); any difference sets `syncstat = 1` (`:1098-1104`); `syncstat = 0` when only one player is left (`:1110`). Both the master (slave bytes against its own) and each slave (its own against the master's) detect a mismatch; peer-to-peer machines compare all.
- **The message:** `printext256(… "Out Of Sync - Please restart game" …)` and a second line (`:1112-1116`), **on the screen only**: there is no `buildprintf`, so a headless test cannot see it, and a hidden tab draws nothing. `syncstate` ("Missed Network packet!", `src/game.c:1117-1121`) is mmulti's obsolete variable (`jfbuild/src/mmulti.c:641`) that nothing sets, so that message never appears.
- Nothing resets `randomseed` except `resetprestat` (`src/premap.c:645`: `randomseed = 17`) and loading a saved game (`src/menues.c:365`). `krand()` is `jfbuild/src/engine.c:9693-9696`; `TRAND` is `krand()` (`src/duke3d.h:202`). Drawing and menu code in `src/` never calls `TRAND`/`krand` (the only `game.c` users are the simulation: `spawn`, the glass helpers, `domovethings`; `src/premap.c:448` is spawn-point choice).

### 2.6 `waitforeverybody()` (`src/premap.c:1288-1316`)

`return` if `numplayers < 2`. Send packet 250 to every other player, or only to the master if a slave in M/S mode (`src/premap.c:1293-1298`); `playerreadyflag[myconnectindex]++` (`src/premap.c:1299`); then `while (1)`: `handleevents()` (`src/premap.c:1303`), **`gameexit("")` on a quit event or Escape** (`src/premap.c:1305`), `getpackets()` (`src/premap.c:1307`), done when every player's counter has caught up (a slave in M/S mode only waits for the master, `src/premap.c:1309-1314`). ### 2.7 Version checks

`BYTEVERSION_JF 132` (`src/duke3d.h:66`); `BYTEVERSION = 132 + (PLUTOPAK ? 1 : (VOLUMEONE << 1))` (`src/duke3d.h:68`): regular 132, Atomic 133, shareware 134. `PLUTOPAK` is `conversion == 14` (`src/duke3d.h:51`), and `conversion` is set by the **compiled CON scripts** (`src/gamedef.c:31` default 13, set to 14 at `src/gamedef.c:1512` when the `gamestartup` command has the Atomic Edition's extra parameters, `src/gamedef.c:1495-1515`). `VOLUMEONE` is the identified GRP being the shareware (`src/duke3d.h:52`, `src/game.c:7856`). So the version byte covers the **GRP kind and the CON flavour**, not their contents. Checked at: packet 6 (`src/game.c:642`, gameexit on mismatch), demo open (`src/game.c:8173-8183`, prints "Demo is for …" and refuses), saved-game load (`src/menues.c:217`, FTA message 114).

## 3. Network set-up

### 3.1 How `networkmode` is chosen

- The game never chooses. `networkmode` is mmulti's variable (`jfbuild/src/mmulti.c:91`, initially -1) and is set from the arguments by `initmultiplayersparms` (`jfbuild/src/mmulti.c:723-885`): `-nm` / `-n0` = **master/slave**, `-nm:N` = N players (2..`MAXPLAYERS` 16, else "Invalid number of players", `jfbuild/src/mmulti.c:752-775`); `-np` / `-n1` = **peer-to-peer** (`jfbuild/src/mmulti.c:776-780`); a host name with no `-n` argument defaults to M/S with 2 players (`jfbuild/src/mmulti.c:861`); a relay (`-relay`, `-host-room`, `-room`) forces M/S and the room's player count (`jfbuild/src/mmulti.c:786-797`) and refuses `-np` (`jfbuild/src/mmulti.c:789-792`). The constants are `MMULTI_MODE_MS 0`, `MMULTI_MODE_P2P 1` (`jfbuild/include/mmulti.h:12-13`).
- **There is no rule by player count.** M/S works for 2 to 16 players. **Peer-to-peer works only for exactly 2** (`jfbuild/src/mmulti.c:879-884` returns 0 unless M/S with 2+ players, or `numplayers == 2`). The message at `src/game.c:9082` ("This only happens in 5-8 player mode as a different network scheme is used") is old text: it is printed when the master leaves **any** M/S game (`if (j < 0 && networkmode == 0)`, `src/game.c:9081`).
- The game reads the mode as `!networkmode` ("M/S") at `src/game.c:418, 464, 570, 603, 633, 668, 683, 2201, 2210, 6572, 6598, 7627`, `src/menues.c:1379, 3764, 3879, 3919`, `src/premap.c:1297, 1312`, as `== 1` (peer) at `src/game.c:841`, and as `== 0` at `src/game.c:9081`. In M/S mode the master re-transmits packets 126, 4, 5, 6, 7, 8 to the other slaves (§2.2).

## 5. Level end: every `MODE_EOL` writer and the path through `moveloop`

`MODE_EOL` is 8 (`src/duke3d.h:150`). Writers (all of `src/`):

| Where | Context | Writes |
|---|---|---|
| `src/player.c:2493` | `processinput`, after the end-of-level button anim: `p->fist_incs > 42` (`src/player.c:2465-2497`) | `ps[i].gm = MODE_EOL` for **every** player (`src/player.c:2492-2493`); next level number set at `src/player.c:2467-2491` |
| `src/player.c:2516` | `processinput`, `p->timebeforeexit == 1` (`src/player.c:2500-2529`); `timebeforeexit` is set by the CON command `endofgame` (`src/gamedef.c:2577-2582`, which also sets `ud.eog = 1`) and by a sector with `lotag == -2` (`src/sector.c:2958-2962`) | every player (`src/player.c:2515-2516`); level number `src/player.c:2517-2527` |

| `src/sector.c:1394` | `checkhitswitch`, `lotag == 65535` (`src/sector.c:1392-1409`) | **only `ps[myconnectindex]`** (and `ud.level_number`), returns 1 |
| `src/game.c:6092`, `src/game.c:6395` | `cheats()`: the "level" and "end game" cheat codes | `ps[myconnectindex].gm` |

The cheat codes only run when `numplayers < 2 && ud.recstat == 0` (`src/game.c:6407`, `src/game.c:5996`), so in a network game the live writers are the first four. All four run **inside `domovethings()` on every machine** (`processinput`, `checksectors`, `checkhitswitch` are simulation), and each sets the next `ud.level_number`/`ud.m_level_number` there too. The one writing only `myconnectindex` is consistent because each machine reads only its own `gm` (`src/game.c:8061`).

**The path:** `moveloop()` (`src/game.c:8464`) has the loop `while (movefifoend[myconnectindex] - movefifoplc > bufferjitter)` calling `domovethings()` (`src/game.c:8474-8480`) and **never tests `MODE_EOL`**. The write replaces the whole `gm` word (`= MODE_EOL`), which clears `MODE_GAME`, but the main loop only tests `gm&MODE_GAME` before the *next* `moveloop()` call (`src/game.c:8058`). So after the tic that sets `MODE_EOL`, the same `moveloop()` call keeps running every further tic whose inputs have arrived (and that has a buffer margin of `bufferjitter`); how many that is depends on how many tics the master had already forwarded, which differs by machine and by timing. Only then does the main loop see `MODE_EOL` (`src/game.c:8061`): `closedemowrite()` (`:8065`), `ready2send = 0` (`:8067`), `dobonus(0)` (`:8073`, §4), the episode-end handling (`:8075-8093`), `enterlevel(ps[myconnectindex].gm)` (`:8098`).

This is the same pattern as jfSW's L20 (`bugs.md`): machines can play different numbers of tics after the exit. What carries over into the next level in a co-op game (and in single player) is each player's weapons, ammo and inventory (`resetprestat` resets them only `if ((g&MODE_EOL) != MODE_EOL && numplayers < 2) || (ud.coop != 1 && numplayers > 1)`, `src/premap.c:656-660`) and health (`resetpspritevars`: `s->extra = ps[j].last_extra` after an exit, `src/premap.c:1195-1200`), so extra tics played after the exit change what a player has in the next level. **Confirmed by a test, and fixed, in brief A1: bugs D5 and D6, §17.1** (the second one is a hang at the level end that this section did not foresee).

## 12. Surprises and candidate entries for `bugs.md`

1. **`-nosetup` does not stop the startup window on a first run** (no `duke3d.cfg`): `configloaded < 0` opens it (`game.c:7809`). Headless runs unset `DISPLAY`.
2. **Quit during the network wait** returns from `Startup()` and then from `app_main` with initialisation unfinished (`game.c:7571-7574`, `:7904-7905`); jfSW's L4 has the same shape.
3. **SIGTERM / window close is the Escape key** in the game loop (`:8049-8052`), so it opens the menu instead of quitting; `waitforeverybody` and the startup wait do honour it (`premap.c:1305`, `game.c:7571`).
4. **Packet 8 (user-map game):** the sender writes the map name from byte 10 (`menues.c:3758`) and sends `10 + len` bytes; the receiver reads `ffire` from byte 10 (`game.c:696`) and copies the name from `packbuf+10` but with length `packbufleng - 11` (`:698-701`): friendly fire becomes the first character's ASCII value and the last character of the name is dropped. User-map network games only.
5. **A demo never exits by itself** (§9), unlike jfSW's.
6. **`newgame` waits for the skill-choice sound to end** (`premap.c:1024`) and the E3 end sequence waits for five voice clips (`game.c:9430-9442`): with a stalled mixer (a suspended browser audio context) these spin.
7. **Shareware quit shows two order screens** that wait for keys (`game.c:2088-2089`), also after a network error exit.
8. `myname` is not re-sent after a change (`osdcmds.c:352`); `auto_aim` and `weaponswitch` are sent once, in packet 6.
9. `MAXGROUPFILES` is 4 (`cache1d.c:389`): the main GRP plus three `-g` files.
10. Peer-to-peer mode is limited to 2 players by mmulti (§3.1), though `game.c` has the 3-or-more-player code for it.

## 15. What brief 01 added and learnt

Brief 01 (`01-native-relay.md`) changed the game only; line numbers are `src/` at `browser/01-native-relay`. New files: `src/netgame.c`/`.h` (the shareware gate, relay failures, the sync log) and `src/testhooks.c`/`.h` (test-only hooks).

### 15.1 Where things are now

- **Arguments** (`checkcommandline`, `src/game.c`): `-testquit<N>`, `-testsync`, `-testnudge<T>`, `-testdump<name>`, `-teststate[<T>]` and `-allowsharewarenet` are matched **before** the big `switch (*c)`. They have to be: any other `-t…` is the respawn option (`case 't'`, "Respawn on"), `-a…` is "other player AI", `-r…` records a demo and `-h…` names a DEF file. For the same reason `-relay`, `-room` and `-host-room` **outside `-net`** are refused with a message (`-net`'s branch skips them when they follow it). **Test-only arguments, and `-allowsharewarenet`, go after `--` (or before `-net`)**: what follows `-net` up to `--` belongs to mmulti (§3.2).
- **`app_main`**: the early gate before `initmultiplayersparms` (`NetGameAllowedFor(gamegrp->game)`, only when no startup window will run; nothing has been opened, so a refused relay host makes no room), then `NetFailIfRelayFailed()` when the arguments are bad (so the game exits 1 instead of starting a single player game), the authoritative gate after **every** group file is mounted, `-g` extras included (`NetGameAllowed()` -> `NetDataIsShareware()`: `VOLUMEONE` or a `DUKESW.BIN` openable from anywhere; covers the startup window's Join and Host; `gametype` is never changed: a `-g` shareware GRP with no main GRP leaves `gametype` DUKE, i.e. the game believes it is registered), `Startup()`: `mmulti_vnet_setplayercap(VOLUMEONE ? 4 : MAXPLAYERS)` before the wait and `NetFailIfRelayFailed()` after it. The engine's own limit for `-host-room` is **8** (`MAXROOMPLAYERS`, `jfbuild/src/mmulti_vnet.c`), though the game allows 16 over plain UDP.
- **Main loop and `waitforeverybody`** call `NetLostCheck()` (relay session FAILED and `movefifoplc` unchanged for 2 s: message, `uninitmultiplayers()`, exit 1). Nothing tells the *other* players: a host that vanishes still stalls the rest (as jfSW's L18 left it).
- **`checksync()`** calls `NetSyncDiffers()` and `NetSyncChecked()`: `GAME OUT OF SYNC: sync check N (tic T), player P differs from the master` is logged for the first difference of each run of mismatches (§2.5's "on the screen only" is no longer true), and `NetSyncChecks` / `NetSyncMismatches` count. **Every machine compares** (§13, item 3): the master each slave's byte against its own; a slave its own against the master's, so a slave other than the diverging one never sees it (`test-desync.sh`).
- **`domovethings()`**: `TestTicHook()` just before `lockclock += TICSPERFRAME` (after the multiplayer save/load block, which can `return 1` without running a tic): the `-testnudge` and the `-testdump` record, before `movefifoplc++`; the sync byte is `TestSyncByte()` instead of the usual one when `-testsync` is on, taken **every tic** (`syncval` is a ring of `MOVEFIFOSIZ` = 256 bytes, so at most 256 tics may be in flight); `TestTicEnd()` just before `return 0`: `-testquit`. A quit calls `gameexit("")`, which skips the shareware order screens and the deathmatch totals (`*t == 0`), still runs `allowtimetocorrecterrorswhenquitting()` (about 0.3 s) and writes the config; before it a network game keeps acknowledging and resending for 1.5 s so a player a few tics behind can finish.
- **Packet 6** carries `BYTEVERSION + TestVersionSalt()` (8 with `-testsync`, else 0), checked on receipt: a player without the same `-testsync` is refused ("You cannot play Duke with different versions."). `-testquit` values need not match (a player that stops early stops the others, as in jfSW).
- **The tic counter** in `-testdump` and `-testquit` is `movefifoplc` (+1 in the dump), which `clearfifo()` zeroes in `enterlevel`, so it starts again at 1 in each level. It is the same in single player and in demo playback (`playback()` calls `domovethings()` too).
- The `.state` text (`-teststate`) and the hashes are made from one list of fields (`WalkState`, `src/testhooks.c`).

### 15.2 The `-testdump` file

`<name>`, 32 bytes per game tic, eight little endian 32 bit words: `tic` (1-based, from the start of the level), `randomseed`, then 32 bit FNV-1a hashes (over little endian 32 bit words) of `players` (`ps[]` of every connected player), `sprites` (every sprite in use, and the status and sector list orders), `hittype` (`hittype[]` of the sprites in use), `sectors`, `walls` and `other` (`ud`'s game fields, `global_random`, `everyothertime`, `earthquaketime`, the animation, cycler, animated wall and sprite-queue tables, `frags`, `po[]`, the player list). The record is of the state **before** the tic is moved. jfSW's record is 17 bytes (tic, nine sync bytes, one hash); Duke's has more parts because Duke has no nine sync functions and because a test that finds a difference should say which table. `tests/tools/testdump.py diff A B` prints the first differing tic and parts.

### 15.3 State that differs between machines (found by running two machines and diffing; input for A1)

Each was the **first difference** two idle machines showed, and each is left out of the hash with a comment in `src/testhooks.c`:

1. `hittype[i].dispicnum`: written by `animatesprites()` (`src/game.c:5747-5760`, `:5934`) to the picture last drawn, so it is what this machine has drawn so far. Drawing writes the simulation's tables.
2. `sprite[i].yoffset` of a player's sprite (`statnum` 10): `animatesprites()` writes it while the player is in the air (`src/game.c:5594-5595`).
3. `hittype[i].temp_data[0..5]` of the ambient sound sprites (`statnum` 11, `MUSICANDSFX`): `movefx()` (`src/actors.c:1158`) keeps T1, T2 and T5 as audio bookkeeping from this machine's `SoundToggle`, `AmbienceToggle`, free voices and the view point (§7's table). ### 17.1 The level exit (§5's open question, answered)

§5 suspected jfSW's L20 here. It is there, and there is a second bug next to it:

- **D5, real, fixed.** `moveloop()` played every tic with inputs after the tic that set `MODE_EOL`. - **D6, real, fixed.** The master forwards tic inputs from `faketimerhandler()` only, after it has played them when a slave's inputs arrive late, and the main loop sets `ready2send = 0` at `MODE_EOL` before the next `faketimerhandler()`. Fix: the master's loop is `sendmasterpackets()` (`src/game.c:999`), called from `faketimerhandler()` (`:995`) and, for the tics played, from the `MODE_EOL` branch (`:8162`).
- **Every `MODE_EOL` writer runs inside the simulation on every machine.** `player.c:2493` and `:2516` (`processinput`, run for every player by `domovethings()`), `sector.c:2942` (`checksectors`, every player) and `:1394` (`checkhitswitch`, called by `checksectors` and by weapons hitting a switch, both simulation; it sets only `ps[myconnectindex].gm`, which is the only `gm` a machine reads, and the level number on every machine), `gamedef.c:2577` (CON `endofgame`, sets the countdown that `player.c:2516` runs). The cheats (`game.c:6117`, `:6420`) only run with `numplayers < 2`. `fakedomovethings()` calls none of them. No writer sets it outside a tic in a network game; new games from the menu (packets 5 and 8) start a level from `getpackets()` at a moment of their own on each machine, as before.
- **What the fixed game does at the exit.** Every machine plays exactly the tics up to the one that ends the level; the master sends the slaves what it has played and not yet forwarded (not beyond: `upto = movefifoplc`), then `ready2send = 0`. The `-testquit` hook does the same for its last tics (`testhooks.c:633`), which also ends the old "one tic short" quit race that `test-three-games.sh --udp` and F-D1 noted.

Both fixes act before `dobonus()` and do not depend on the game mode; what a DukeMatch carries over is the frag counts (`clearfrags()` runs in `enterlevel`, after the bonus screen prints them).

## 18. Found in brief 03 (data download, CON scripts from the GRP only, native against wasm)

1. **CON scripts come from the GRP only in the browser build.** `loadefs()` and the `include` handler (`src/gamedef.c`) call `kopen4load(name, CONFROMGRPONLY)`. `CONFROMGRPONLY` is `loadfromgrouponly` as before in the native build, and under `__EMSCRIPTEN__` it is `(LooseConAllowed ? loadfromgrouponly : 1)`: `kopen4load`'s second argument 1 means "the first group file only" (§6.3), so a loose `game.con`, `DEFS.CON` or `USER.CON` in the current directory or on the search path is never opened, and `-x<file>` can only name a script inside the GRP. The same macro replaces `loadfromgrouponly` in the "Use default CONs instead?" tests, so the shareware CON's one warning (§6.3) no longer reaches `wm_ynbox` in the browser. `loadfromgrouponly` itself is untouched and still governs demos (`opendemoread`) and sounds, which are read from disk first as before. `LooseConAllowed` (defined in `src/gamedef.c`) is set by the argument `-testloosecon` (`src/game.c`, with the other test arguments, before the `switch`); the page passes it only in test mode. Natively the argument does nothing (loose CONs always override there). Other loose files (`.art`, `.map`, sounds, `duke3d.def`, `DUKE.RTS`) are still read from disk first: the browser keeps them out because the page writes no loose file outside test mode (`writeLooseFile()` in `web/jfduke3d.js`), not because the game refuses them.
2. **The names matter.** `GAME.CON` is opened as `game.con` (`confilename`) but includes its files as written in the script: `DEFS.CON` and `USER.CON` in capitals. The browser's file system is case sensitive, so a loose copy has to be named like that to be found (`tests/web/con.js` does). The game prints the sizes it read: `Compiling: game.con (99639 bytes)`, `Including: DEFS.CON (28893 bytes)`, `Including: USER.CON (36960 bytes)` for the shareware GRP, which is how the tests tell the GRP's script from a loose one.
3. **A missing CON script crashes the game** (`-x` of a file that does not exist): `loadefs()` calls `gameexit()` before the video mode exists, and `showtwoscreens()` divides by zero (`bugs.md` D16). Natively SIGFPE, in the browser the trap shows as "The game could not start: divide by zero." and the output has no "Missing con file" line.

## 19. Random numbers and the order of evaluation (F-D15)

**The rule: never draw two random numbers in a place where the C standard does not say which comes first.** `TRAND` (`krand()`), `rnd(X)` and every function that calls them (`spawn()`, the CON interpreter's `execute()`, ...) change the seed, so the order of two draws decides the values. The standard leaves the order open for:

- the arguments of one call (`EGS(..., TRAND&255, ..., TRAND&2047, ...)`), and an argument against the called function's own expression;
- the two operands of any binary operator except `&&`, `||` and `,` (`(TRAND&1)<<10) + (TRAND&255)`), and the two sides of an assignment, also a compound one;
- the operands of an array subscript and the elements of an initialiser list.

Sequenced, so fine: separate statements, separate declarators of one declaration (`int a = TRAND&3, b = TRAND&3;` draws `a` first), the operands of `&&`, `||` and `,`, the condition of `?:` against its branches, and the arguments of a call against what the called function does inside (`f(TRAND)` with `f` drawing numbers is fine).

**What goes wrong.** gcc on x86-64 evaluates the arguments last to first (and the right operand of a binary operator first) at every optimisation level; clang, so Emscripten, first to last. Before F-D15 there were 36 such places (15 uses of `RANDOMSCRAP` and 21 other calls and expressions; the list is in `F-D15-krand-order.md`), so a gcc build, a clang build and the browser's gave different debris, glass and gibs for the same demo, and a game between them desynced (`bugs.md` D15). MSVC's order is not known; the original DOS compiler's is not known either.

**What the code does now.** Every one of those places draws each number into a local first, in its own statement, in **gcc's order**: last argument first. That keeps native Linux games and demos exactly as they were (the gcc-native `-testdump` of the same demo is byte for byte the same before and after) and makes every other compiler agree with them. Locals are named `r0`, `r1`, ... in the order of the arguments they replace (`rs0`... inside `RANDOMSCRAP`, which is now a `do { } while(0)` block because it needs them), and they are assigned from the highest down. The codebase is C89 in style (no mixed declarations): the locals are declared at the top of the function or of a block.

**Writing new code.** Draw a number into a local with an assignment of its own, and use the local. If two draws are meant to be in one expression, decide which comes first and write it so. `tests/tools/krand-order.py` (clang, 15 seconds, run by `make test`) lists every place that still breaks the rule: it must print none; `tests/tools/krand-equiv.py OLD_TREE NEW_TREE` shows by AST that a rewrite draws the same numbers in the same order. `tests/web/determinism.js` (gcc native against wasm) is the check that bites: debris, glass and gibs of a scripted player with every weapon (`-testarm`).

**Not changed, and why.** The engine's `krand()` is in `jfbuild` (shared with jfSW): it has no caller there with two draws in one expression (the voxel code uses the C library's `rand()` once per statement, for drawing only). jfSW has the same pattern (`RANDOM_RANGE(140)-RANDOM_RANGE(140)`, `weapon.c:10190-10192`, `:11643-11645`), see the F-D15 Outcome.

### 20.2 The hidden pass

`app_main`'s loop (`src/game.c:8231`): `handleevents()` (in a hidden tab with a relay session it waits for a vnet wake-up, 20.1) -> `NetLostCheck()` -> `moveloop()` (receive, and move every tic whose inputs are in) -> the level-end block -> **`if (NetHiddenTab()) { HiddenNetPass(); continue; }`**, which skips `cheats()`, `nonsharedkeys()`, `displayrooms()`, `displayrest()`, `checksync()` and `nextpage()`. `HiddenNetPass()` does what the drawing half did for the network:

- **`faketimerhandler()`, once for every input that is due by this tab's own clock (at most 8).** Duke's input for a tic is made and sent by `faketimerhandler()` (`src/game.c:787`), which the main loop calls after `nextpage()` and the engine calls from inside its long drawing loops (§2.3); a pass that draws nothing must call it itself or the room waits for this player's input. It runs *after* `moveloop()` here (jfSW's pass runs it first): the loop is cyclic, so the order only matters for the first pass after the hide.
- **`checksync()`.** The sync bytes are a ring of `MOVEFIFOSIZ` (256) entries, and `checksync()` is only called from the drawing half of the loop; a tab that never compared would let the ring wrap (256 tics with `-testsync`, 2048 without it) and report false differences when it was shown again. (jfSW has no such ring.) `checksync()` calls `printext256()` only when it has something to say; that draws into a frame nobody sees and is harmless.
- **`mmulti_vnet_flush()`**: mmulti puts at most one datagram per peer on the wire every 25 ms (`PAKRATE`), and `getpackets()` (called by `faketimerhandler()` before it makes the input) can spend that window on an acknowledgement; without the flush the input would wait for the next network event. 04b generalises this to every tab.
- **Not done in a hidden tab:** the menu (`displayrest()` opens and closes it on the Escape key; no key reaches a hidden tab), typing (`typemode()`), the automap, `cheats()` (single player only), the screen-size and detail keys. None is simulation. (`getinput()` makes zero inputs while the menu is open, `player.c:1878-1888`, so a hidden tab in the menu still sends them.) The bonus screens wait for a key and still hold a hidden tab up (a DukeMatch level end; brief 05, L23); in co-op `dobonus()` returns at once (§4).
- **`-testnodraw`** makes `NetHiddenTab()` true natively too (in a network game), so the same pass is tested without a browser: `tests/net/test-nodraw.sh`. Natively the pass spins (`handleevents()` does not wait); that is for tests only.
- A hidden single player game does not get here: `jfbuild_browser_hidden_netgame()` needs a relay session, so it still pauses in the yield (about 10 tics a second).

### 20.6 A level exit with a late input (D11, fixed)

A slave's input for a tic is made and sent a tic or two before the slave plays that tic, and an input packet carries no tic number (§2.2, cases 0 and 1: it is appended to the sender's queue). When the exit tic is played, the slave has already sent its inputs for the tics after it. The master plays the exit tic as soon as it has every input for it, leaves the level, and in `enterlevel()` clears its queues (`clearfifo()`, `src/premap.c:1540`) shortly before `waitforeverybody()`. A slave's input for the old level that reaches it after that clear is appended to the *new* level's queue as that slave's input for its first tic, and the slave plays its own, different input there: the master and the other slaves have the slave's player somewhere else than the slave has, from tic 2 of the new level on. Found when the browser test `level-exit-slave` (a browser slave stopped for 1.5 s at tic 190; the browser master leaves the level faster than a native one does) desynced in 1 game of 7; made deterministic with `-testlate`; fixed by `fix/level-exit-stale-inputs` (`bugs.md` D11). A1's stall (`-teststall`) stops a machine in the middle of a tic, so no input of it is ever in flight: its test could not see this.


## 21. Lag cuts (brief 04b)

Line numbers are `src/` at `browser/04b-lag-cuts`. jfSW's brief 04b is the template ([`04b-lag-cuts.md`](04b-lag-cuts.md) here has the Outcome with the numbers).

### 21.1 Where an input waited, and what changed

- **The input waited for mmulti's send window.** `faketimerhandler()` calls `getpackets()` (`src/game.c:847`) before `getinput()` makes the input; `getpacket()` calls `dosendpackets()` for every peer first (`jfbuild/src/mmulti.c:1184`), and when the 25 ms window (`PAKRATE`) has passed that puts a datagram with only acknowledgements and resends on the wire; the input's own `sendpacket()` then finds the window used and queues. It left at the next `dosendpackets()` after the window: 13 to 14 ms at the median for a native machine, 23 to 30 for a browser (a frame or two), **a slave pays it going to the master and the master pays it again coming back**. Fixed by `SendInputNow()` (`src/game.c:459`): `mmulti_vnet_flush()` right after the peer-to-peer packets 16 and 17 (`:980`), the slave's packet 1 (`:1043`), and once at the end of `sendmasterpackets()` (`:1162`) when it sent a tic. It sends what `sendpacket()` queued, ignoring the window, for every peer (relay or plain UDP); a datagram with only acknowledgements still goes at most once per window.
- **The master forwarded a tic only at its own timer tick.** `sendmasterpackets(0x7fffffff)` was called from the end of `faketimerhandler()` only (and `sendmasterpackets(movefifoplc)` from the level-end branch and `-testquit`, A1's D6). A slave's input that arrived just after the master's tick, and was the last one missing for a tic, waited for the next tick (mean 7 to 21 ms, p95 20 to 31 ms in the measurements). Fixed: `getpackets()` ends with `sendmasterpackets(0x7fffffff)` for the master in master/slave mode when `ready2send` is set and no barrier is running (`inbarrier`, `:833`), **after** the receive loop: `packbuf` is both the receive buffer and `sendmasterpackets()`'s send buffer, and a forward from inside the loop would overwrite a datagram that is being read (its sync bytes are read after the input; the mutation in the Outcome shows it).
- **The hidden pass no longer flushes** (§20.2): every tab flushes each input as it makes it, so `HiddenNetPass()` ends with `checksync()` only; the four hidden scenarios pass without the flush.
- **`ready2send` is load-bearing.** `sendmasterpackets()` does not know whether a level is running: `playerquitflag[]` is 0 until the first `enterlevel()` ends, so without that condition the master "forwards" empty tics from the start-up barriers and every network game fails at start (mutation in the Outcome; `bugs.md` D19). `ready2send` is 0 from the start of the program (until the first `resettimevars()`) and from the level's end (`MODE_EOL` branch) until the next level has started.
- **The 127 nudge (fix round).** `faketimerhandler()` sends a one byte packet 127 to every slave at each tick at which the next tic is still incomplete ("allows packet resends"; ignored on receive). A tick at which the master had already passed a tic on from `getpackets()` used to send that tic and no nudge; with step 3 it sent the nudge **as well**, one more reliable packet per tic. At 400 ms of latency and more on the slave's datagrams the packets in flight (every datagram resends all unacknowledged packets, at most 256 bytes with the header) no longer fit, the newest tics were held back until older ones were acknowledged, and the slave's lag correction fell behind further and further (`otherminlag` and `bufferjitter` climbing past 50; its game ended before the master's last tics reached it). The nudge is now sent only at a tick that forwarded nothing (`masterfwdsincetick`, `src/game.c:449`, `:1056`): the same packets as before step 3. Evidence: with `MAXPAKSIZ` 576 (a scratch build of the fork) the unfixed step 3 passed; with the nudge removed from the ticks that forwarded it, it passed. The remaining limit is the original game's: the same stall happens with the baseline and with step 2 at about 640 to 690 tics at 500 ms (all three builds), because a datagram of 256 bytes cannot hold an RTT's worth of packets at 30 tics a second. Not fixed here (an engine change; `bugs.md` D20).
- **What does not change.** The same function builds the same packets: tic `movefifosendplc` goes out only when every live player (the master included) has an input for it, in order, and `movefifosendplc` advances by `movesperpacket` per packet, so a batch (`-f2`, `-f4`) always goes whole. The bytes that depend on *when* the master sends are the lag-correction bytes of every 32nd tic (`TIMERUPDATESIZ`: each slave's `myminlag` so far; it is reset when sent) and which of the master's pending sync bytes ride in which packet (all that are pending, appended to the next packet); both followed the master's timing before and neither is game input. Every `-testdump` of every scenario is identical on all machines.
- **The level-change rules.** The new call is gated on `ready2send`, which the main loop clears at `MODE_EOL` before anything can send (D5: nothing is forwarded after the exit tic; D6: the `MODE_EOL` branch still sends what has been played, first), and on **`inbarrier`** (fix round), a counter that `waitforeverybody()` (`src/premap.c:1296`, `:1319`) keeps while it runs. Why the second one: `ready2send` is still 1 in `newgame()`'s first barrier (`premap.c`: `waitforeverybody()` runs before `ready2send = 0`) and in `saveplayer()`'s two barriers, and the master's own queue is full there. `newgame()` is reached in the middle of a game by the menu's "start game" and by a packet 5 or 8 from a slave; a slave's inputs of the running game that are still on their way reach the master inside that barrier, and without the flag the nested `getpackets()` would forward them **after the master's ready packet** (measured: tics 101 to 108 at 500 ms; `-testnewgame`, DIAG print). Before 04b nothing was forwarded in a barrier. A packet 0 carries no tic number and has no `waitingfornewlevel` guard (only packet 1 has: D11), so one that reaches a slave after the slave's `clearfifo()` would be taken for a tic of the new level. Whether it does depends on the slave's load time against the latency (the slave's `flushpackets()` before its second barrier drops what has arrived by then), so the race was **not** forced into a desync by a test (a build without the flag, with 700 ms on the slave's datagrams, hung the master and crashed the slave once, together with the nudge problem below; with only the flag removed all runs agreed); the scenario `newgame` checks the rule itself: the game logs `TEST: the master forwarded tic N inside a barrier` if it ever happens, and the mutation fails 3 games on it. With the flag the barriers of `saveplayer()` forward nothing, as before 04b (the first version of 04b forwarded complete tics inside them: the same tics, sooner). `loadplayer()`'s and start-up barriers forward nothing in any case (the master's own queue is empty after `clearfifo()`, or `ready2send` is 0).

### 21.2 The instruments

- **`-testlag<name>`** (`src/testhooks.c`): 36 bytes per game tic, nine little endian 32 bit fields from this machine's own `CLOCK_MONOTONIC` (microseconds): tic, made, ready, ran, sendwait, fwdwait, otherminlag, bufferjitter, the sum of the clock corrections. Written 16 tics after the tic (a datagram, and on the master the combined packet, often leaves after the tic has run), the rest at `-testquit`, with a log line per peer: `TEST: lag: N datagrams (B bytes) to player P in T ms: A with new data, C paced (acks and resends only), R of those just before one with new data in the same receive pass`. It uses the two observation hooks that the jfbuild fork has had since jfSW's 04b (`mmulti_test_queuehook`, `mmulti_test_sendhook`): **no fork change**. Input to tic is `ran - made`. With `movesperpacket` > 1 a repeated input keeps the time of the one it repeats. Nothing goes on the wire and nothing changes without it.
- **`-testslowstart<ms>`**: this machine waits when its level has started (`resettimevars()`, after the barrier) and before its first frame, with its clock running (a busy wait natively, `emscripten_sleep` in the browser), after flushing mmulti. A machine with `-testdump` logs `TEST: frames drawn before tic 1 of level N: F` (the frames drawn since its level started; the state dumps are not touched: the level-exit test compares their blocks whole).
- **Prefixes.** Game options are matched by `Bstrncasecmp(c, "testxxx", n)`; neither new name is a prefix of an existing one or the other way round (`-testlate`/`-testlag` share `-testla`). The `-net` sub-options are skipped by the game's own parser, so there is no jfSW-style skip list.
- **`netplay.js`:** `lag` (checked bounds on the mechanisms), `lag-batch` (`-f2`, `-f4`), `tic1`, and by name `lag-matrix` (`NETPLAY_LAG_ONLY`, `NETPLAY_LAG_REPS`, `NETPLAY_LAG_EXTRA`, `NETPLAY_LAG_TAG`); variants of the game are run with `NETPLAY_GAME` and `WASM_DIR`.

### 21.3 Things seen

- **The lockstep buffer is the largest remaining cost** and moves in whole tics (33.3 ms): a browser machine's `bufferjitter` is 2 to 4 tics (it follows the worst lateness seen in 32 tics) and the delay a player feels is quantised accordingly. In browser pairings the end-to-end figures move by a tic or more between two runs of the same build; the mechanisms (send wait, forwarding wait) are the steady measurements.
- **The datagram rate** goes from 29 to 40 a second per peer to 50 to 60 (1.4 to 2.0 times), one per input plus the acknowledgements. Many of the extra ones are redundant, as in jfSW: `getpacket()` spends the window on an acknowledgement just before the input's own flush sends the same acknowledgements with new data (the `-testlag` line says how many).
- **The tic-1 check** found no difference (see the Outcome): Duke's first frame writes nothing the simulation reads, as 04's audit said, and `enterlevel()` draws a frame (`displayrooms()`) on every machine before the level starts anyway.
